# Архитектурные схемы

## Генерация диаграмм

Все диаграммы хранятся в виде `.puml`-исходников в директории [`diagrams/`](diagrams/).
SVG-файлы генерируются автоматически и коммитятся рядом с исходниками.

**GitHub Actions workflow** ([`.github/workflows/plantuml.yml`](../.github/workflows/plantuml.yml)):
- **Pull Request** — рендерит все `.puml`-файлы для проверки синтаксиса; при ошибке сборка падает. Сгенерированные SVG загружаются как артефакт (`plantuml-diagrams`).
- **Push в `main`** — рендерит диаграммы и автоматически коммитит изменённые SVG-файлы в ветку.
- **Ручной запуск** — доступен через вкладку Actions → `PlantUML Diagrams` → `Run workflow`.

**Локальный рендеринг** (требуется `plantuml`):
```bash
brew install plantuml        # macOS
bash schemas/render-diagrams.sh
```
Скрипт генерирует `.svg` рядом с каждым `.puml`-файлом.

## Текущая монолитная архитектура

Текущая система Warmhouse реализована как монолит: единый Go-процесс объединяет API для пользователей, логику работы с датчиками и доступ к данным в одной PostgreSQL-базе.

С системой взаимодействуют три внешних участника:

- **Пользователь** — просматривает показания датчиков через веб-интерфейс.
- **Администратор** — управляет конфигурацией датчиков (добавление, удаление, обновление) через то же API.
- **Умные устройства** — физические датчики (на текущий момент только температурные), которые напрямую отправляют значения и статус через HTTP PATCH-запросы. Монолит также проксирует запросы к внешнему Temperature API для получения актуальных показаний.

Все ответственности сосредоточены в одном процессе: маршрутизация, бизнес-логика, хранение данных и интеграция с внешним сервисом. Это создаёт ряд ограничений:

- Невозможно масштабировать отдельные части системы независимо.
- Поддержка новых типов устройств или протоколов требует изменений во всём приложении.
- Отсутствует асинхронная обработка событий от устройств.
- Единственная точка отказа: при проблемах с любым компонентом падает вся система.

Диаграмма контекста: [`diagrams/context/monolith_diagram.puml`](diagrams/context/monolith_diagram.puml)

## Новая микросервисная архитектура

> **Предупреждение.** ACL, а также системы аутентификации и авторизации на этих схемах **не отражены** и в объём работ по архитектуре не входили. Здесь сделан акцент только на микросервисной декомпозиции и взаимодействии компонентов.

Новая архитектура разбивает монолит на специализированные сервисы с чёткими зонами ответственности. Сервисы взаимодействуют через REST API и две Kafka-шины: **Event Bus** (команды и события между сервисами) и **Telemetry Bus** (телеметрия от устройств). Каждый сервис владеет собственной базой данных.

Диаграммы:
- Контейнерная: [`diagrams/container/microsevice_diagram_container.puml`](diagrams/container/microsevice_diagram_container.puml)
- Компонентная: [`diagrams/component/microsevice_diagram_component.puml`](diagrams/component/microsevice_diagram_component.puml)

### Основные сервисы

- `SmartHomeDashboard` — веб и мобильный UI. Единая точка входа для пользователей и администраторов. Все действия передаются в `UserManagementService`.

- `UserManagementService` — основной бэкенд-сервис. Управляет пользователями, домами, комнатами и регистрацией устройств. Принимает запросы от `SmartHomeDashboard` и перенаправляет их в `AutomationOrchestratorService` или `CommandExecutionService`.

- `AutomationOrchestratorService` — сервис проектирования автоматизации (design-time). Принимает запросы на создание и редактирование сценариев, хранит их версии и публикует активные сценарии в `CommandExecutionService`.

- `CommandExecutionService` — сервис исполнения (runtime). Получает ручные команды от `UserManagementService` и активные сценарии от `AutomationOrchestratorService`. Подписывается на `Event Bus` для получения событий устройств, оценивает триггеры и публикует команды для устройств обратно в `Event Bus`.

- `EventProcessingService` — сервис обработки телеметрии. Подписывается на `Telemetry Bus`, нормализует и валидирует входящие события, сохраняет их в базе данных и публикует обработанные события в `Event Bus`.

- `DeviceIntegrationGateway` — интеграционный шлюз, нужен для поддержки контрактов с разными вендроми и их устройствами. Подписывается на `Event Bus` для получения команд, отправляет их на устройства через API или протоколы производителей, принимает сырые события от устройств согласно их контракту и публикует конвертированное событие телеметрии в `Telemetry Bus`.

### Основные сценарии взаимодействия

#### Ручное управление устройством

1. Пользователь отправляет команду через `SmartHomeDashboard`.
2. `SmartHomeDashboard` обращается к `UserManagementService`.
3. `UserManagementService` передаёт команду в `CommandExecutionService`.
4. `CommandExecutionService` публикует команду в `Event Bus`.
5. `DeviceIntegrationGateway` получает команду из `Event Bus` и отправляет её на устройство через API производителя.

#### Создание сценария автоматизации

1. Пользователь создаёт сценарий через `SmartHomeDashboard`.
2. Запрос поступает в `UserManagementService`, который перенаправляет его в `AutomationOrchestratorService`.
3. `AutomationOrchestratorService` валидирует и сохраняет сценарий, затем публикует его активную версию в `CommandExecutionService`.
4. `CommandExecutionService` загружает сценарий и ожидает событий для запуска триггеров.

#### Обработка события от устройства и запуск автоматизации

1. Умное устройство отправляет событие в `DeviceIntegrationGateway`.
2. `DeviceIntegrationGateway` публикует сырое событие в `Telemetry Bus`.
3. `EventProcessingService` получает событие из `Telemetry Bus`, нормализует, сохраняет и публикует в `Event Bus`.
4. `CommandExecutionService` получает событие из `Event Bus`, оценивает триггеры активных сценариев.
5. Если условия выполнены, `CommandExecutionService` публикует команду в `Event Bus`, и `DeviceIntegrationGateway` доставляет её на нужное устройство.
